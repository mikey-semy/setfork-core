# Сплошное ревью ядра

Тот же набор, что в приложении (`setfork-app/docs/review/`), и те же правила: состояние
живёт **на диске, а не в переписке**.

```sh
python3 scripts/review/review.py status      # где мы и какой блок следующий
python3 scripts/review/review.py coverage    # карта «файл → блок»; падает, если файл ничей
python3 scripts/review/review.py check       # манифесты на месте, шаблоны не пустые
python3 scripts/review/review.py prompt C1 --role hunter
```

## Почему ядру нужно отдельное ревью

**У ядра нет второго рубежа.** Продуктовые проверки живут в приложении, а ядро принимает
на веру то, что ему передали: `content` блока хранится непрозрачным JSON, приём пака
проверяет форму дерева. Ошибку в приложении поймает ядро на записи версии; ошибку в ядре
не поймает никто — приложение туда не смотрит.

Это не дефект устройства, а его свойство, и оно задаёт цену: находка здесь дороже такой же
находки в приложении.

## Нарезка: 7 блоков

Плоская — ядро в десять раз меньше приложения, и слои видны по каталогам.

| блок | о чём |
|---|---|
| **C1** приём и запись | вето обходится, запись частична, отказ не доезжает до клиента |
| **C2** проекция и канон | что в git против того, что ядро считает версией |
| **C3** поверхность gRPC | все точки входа сразу: чего нет ни в одной |
| **C4** ворота и лимиты | где ядро доверяет приложению больше, чем следует |
| **C5** хранилище | рукописный SQL против схемы |
| **C6** вход и зеркало | что ядро скрывает о себе; что с версией, когда зеркало недоступно |
| **C7** сборка и выкатка | что собирается против того, что едет на прод |

## Порядок работы

Тот же: манифест → охотник → верификатор → приёмка → починка другим агентом → ревью диффа
теми, кто его не писал. ⚠️ Один агент не ищет и не чинит одновременно. Блок не закрывается
без выполненного критерия приёмки.

Что у нас уже стоило кругов и чего повторять не надо — в `setfork-hq/reviews/problems/CLUSTERS.md`,
корни K33–K41. Сверяться с ними ДО того, как записать находку.
